    Comprendre le déploiement

    Cette page explique comment le code de GitHub arrive en production sur AWS et comment cet accès est sécurisé. Pour les commandes et la configuration, voir Déploiement CI/CD.

    Vue d'ensemble

    À chaque push sur main, le workflow Deploy (../../../.github/workflows/services.yml) enchaîne trois jobs :

    flowchart TD
    PUSH("Push sur main")
    CHANGES("1. changes : quels services ont changé ?")
    BUILD("2. build : une image Docker par service modifié")
    DEPLOY("3. deploy : mise à jour des conteneurs sur l'EC2")
    ECR("ECR : registre d'images privé")
    EC2("EC2 enervision-app")
    NOTHING("Rien à faire")

PUSH --> CHANGES
CHANGES -->|aucun service| NOTHING
CHANGES -->|web, etl-worker...| BUILD
BUILD -->|docker push| ECR
BUILD --> DEPLOY
DEPLOY -->|commande SSM| EC2
ECR -->|docker pull| EC2

classDef ci fill:#fff,stroke:#1971c2,stroke-width:2px
classDef aws fill:#fff,stroke:#f08c00,stroke-width:2px
classDef plain fill:#fff,stroke:#333,stroke-width:1px
class PUSH,CHANGES,BUILD,DEPLOY ci
class ECR,EC2 aws
class NOTHING plain

    Ce workflow ne tourne pas sur les PR : c'est le workflow ci.yml (job call-images) qui construit alors les images des services modifiés, avec les mêmes règles de sélection, pour vérifier qu'elles compilent. Elles ne sont ni publiées ni déployées.

    1. changes : quels services ont changé ?

    Le job compare le commit actuel au dernier commit déployé avec succès, mémorisé dans le paramètre SSM /enervision/prod/deployed-sha, puis confronte les fichiers modifiés aux paths de ../../../.github/services.json.

    flowchart TD
    DIFF("git diff entre le dernier commit déployé et le commit actuel")
    GLOBAL{"Un fichier commun a changé ? compose, workflow, infra/deploy..."}
    MATCH{"Le fichier commence par les paths d'un service ?"}
    ALL("Tous les services")
    SOME("Seulement les services concernés")
    NONE("Aucun service")

DIFF --> GLOBAL
GLOBAL -->|oui| ALL
GLOBAL -->|non| MATCH
MATCH -->|oui| SOME
MATCH -->|non| NONE

    Exemple : un commit qui ne touche que app/web/src/... sélectionne uniquement web.

    Pourquoi le dernier commit déployé et pas le commit précédent ?

    Si un déploiement échoue, le paramètre n'est pas mis à jour : le push suivant compare donc toujours à la dernière version réellement en production et redéploie aussi ce qui avait échoué. Rien n'est perdu.

    2. build : compiler et construire l'image

    Il n'y a pas d'étape de compilation séparée : la compilation a lieu dans le docker build, sur une machine GitHub. Chaque Dockerfile décrit comment compiler son service (multi-stage build). Par exemple ../../../app/web/Dockerfile :

    # Étape 1 : image Node, compile l'application Angular
FROM node:24-alpine AS build
RUN npm ci && npm run build          # produit dist/web/browser (HTML, JS, CSS)

# Étape 2 : image finale, uniquement nginx + les fichiers compilés
FROM nginx:1.27-alpine
COPY --from=build /app/dist/web/browser /usr/share/nginx/html

    L'image finale ne contient ni Node.js ni le code source : seulement ce qui est nécessaire pour servir l'application. La pipeline, elle, ne connaît que docker build puis docker push : un service Java (Maven) ou Python fonctionne de la même façon, seul son Dockerfile change.

    Les services sont construits en parallèle, un job par service, avec un cache des couches Docker entre deux runs (les dépendances ne sont pas réinstallées si elles n'ont pas changé).

    Qu'est-ce qu'ECR ?

    ECR (Elastic Container Registry) est un registre d'images Docker privé, hébergé par AWS : l'équivalent de Docker Hub, mais seules les identités AWS autorisées peuvent y lire ou y écrire.

    Terraform crée un dépôt ECR par service ayant un build dans services.json, dans le compte EnerVision, région Paris (eu-west-3) :

    <compte>.dkr.ecr.eu-west-3.amazonaws.com/enervision/web
<compte>.dkr.ecr.eu-west-3.amazonaws.com/enervision/etl-worker

    Chaque image est poussée avec deux tags :

    Tag Rôle
    <sha du commit> version exacte et traçable : on sait quel commit tourne en production
    latest dernière version, utilisée si aucun tag n'est précisé

    ECR garde les 20 dernières images de chaque dépôt et les analyse (scan des vulnérabilités connues) à chaque push. Les services proxy (Caddy) et db (TimescaleDB) utilisent des images publiques : ils n'ont pas de dépôt ECR.

    3. deploy : du dépôt GitHub au serveur

    GitHub ne se connecte jamais directement à l'EC2 : pas de SSH, aucun port d'administration ouvert. Le déploiement passe par SSM (AWS Systems Manager) : un agent installé sur l'EC2 interroge AWS en sortie pour récupérer les commandes à exécuter.

    sequenceDiagram
    participant GH as GitHub Actions
    participant S3 as S3 enervision-deploy
    participant SSM as AWS SSM
    participant EC2 as EC2 agent SSM
    participant ECR as ECR

    GH->>S3: dépose compose.yaml, compose.prod.yaml, infra/
    GH->>SSM: exécuter deploy.sh pour web sur enervision-app
    EC2->>SSM: une commande pour moi ?
    SSM-->>EC2: deploy.sh sha web
    EC2->>S3: récupère les fichiers de la release
    EC2->>SSM: lit les paramètres /enervision/prod/env
    EC2->>ECR: docker login puis docker pull web:sha
    EC2->>EC2: docker compose up -d web
    GH->>SSM: résultat de la commande ?
    SSM-->>GH: Success et logs
    GH->>SSM: deployed-sha = sha

    Le serveur ne reçoit jamais le code source : seulement les fichiers compose et les images déjà construites.

    Les étapes du job Production

    Après la validation manuelle (environment production), le job enchaîne :

    Étape Ce qu'elle fait
    Datasets ML (DVC) Seulement si prediction-service est déployé : voir ci-dessous
    Fichiers de la release Copie compose.yaml, compose.prod.yaml et infra/ (sans Terraform) dans s3://enervision-deploy-<compte>/releases/<sha>/, avec dataset-release.json le cas échéant
    Identifiants de l'API énergie Recopie les secrets GitHub ENERGY_API_USERNAME / ENERGY_API_PASSWORD dans SSM : GitHub reste leur source de vérité
    Déploiement SSM Lance deploy.sh sur l'EC2 enervision-app pour les services concernés, puis infra/monitoring/deploy.sh sur l'EC2 enervision-monitoring si monitoring est concerné
    Commit déployé Enregistre le SHA dans /enervision/prod/deployed-sha, base de comparaison du prochain déploiement

    Datasets ML (DVC)

    Les Parquet d'entraînement sont versionnés avec DVC (ml-datasets.dvc) et stockés sur S3. Quand prediction-service est déployé, le job :

    1. récupère les Parquet (services/ml-service/run_dvc.py pull) ;
    2. prépare une release de dataset liée au commit (infra/deploy/dataset_release.py prepare) : empreintes des trois fichiers et marqueur de complétude ;
    3. la publie sous ml/datasets/bootstrap/ dans le datalake (scripts/ml/upload-bootstrap.sh), puis vérifie la publication (dataset_release.py verify) ;
    4. après un déploiement réussi, enregistre son URI dans SSM (/enervision/prod/env/TRAINING_BOOTSTRAP_URI).

    Ainsi, prediction-jobs entraîne toujours sur le dataset correspondant exactement au code déployé.

    Sur l'EC2

    ../../../infra/deploy/deploy.sh s'exécute dans /opt/enervision, un seul à la fois (verrou) :

    1. si prediction-service est déployé, vérifie la release de dataset sur S3 : commit, marqueur de complétude et empreintes des trois Parquet ;
    2. reconstruit .env à partir des paramètres SSM /enervision/prod/env/* (droits 600) ;
    3. prépare un deploy.env candidat avec le tag des seuls services déployés (les autres gardent leur version) et, le cas échéant, l'URI du dataset ;
    4. supprime les images qu'aucun conteneur n'utilise (docker image prune -af) avant le pull et à la fin : sans ce nettoyage, chaque déploiement laisse une image par service et par commit sur /var/lib/docker, jusqu'à saturer le volume ;
    5. se connecte à ECR et docker compose pull les nouvelles images ;
    6. pour un nouveau dataset, le charge à blanc avec le code de prediction-jobs avant de l'activer ;
    7. active le candidat (deploy.env) et docker compose up -d sur ces services : les autres conteneurs ne sont pas redémarrés ;
    8. pour MLflow, lance un test de bout en bout (smoke_test.py).

    Retour arrière automatique des jobs ML

    Si une étape échoue après l'activation d'un nouveau dataset, deploy.sh restaure l'ancien tag de prediction-service et l'ancienne URI, puis redémarre prediction-service et prediction-jobs sur l'ancienne version.

    Un retour arrière vers un ancien commit retélécharge son image depuis ECR (20 dernières images gardées par service).

    Fichier sur l'EC2 Contenu
    ../../../compose.yaml, compose.prod.yaml, infra/ copiés depuis S3 à chaque déploiement
    dataset-release.json release du dataset ML, quand prediction-service est déployé
    .env variables de production, reconstruit depuis SSM (droits 600)
    deploy.env registre ECR, tag déployé de chaque service et URI du dataset
    /var/lib/docker volume EBS dédié : images et données TimescaleDB

    Sur l'EC2 de monitoring

    Seuls les fichiers infra/monitoring/ sont copiés sur enervision-monitoring. infra/monitoring/deploy.sh reconstruit son .env depuis /enervision/prod/monitoring/*, puis recrée Prometheus, Loki, Grafana et Caddy pour qu'ils relisent leur configuration (voir Monitoring).

    Sécurité : l'accès de GitHub à AWS (OIDC)

    Le problème

    L'approche classique consiste à créer un utilisateur IAM et à copier sa clé d'accès dans les secrets GitHub. Ces clés sont permanentes : en cas de fuite (log, dépendance compromise…), elles donnent accès au compte AWS jusqu'à ce que quelqu'un s'en aperçoive et les révoque.

    La solution : OIDC, sans aucune clé stockée

    Avec OIDC (OpenID Connect), GitHub prouve à AWS l'identité du workflow avec un jeton signé, et AWS lui remet des identifiants temporaires (1 heure).

    sequenceDiagram
    participant JOB as Job GitHub Actions
    participant GH as GitHub fournisseur OIDC
    participant STS as AWS STS
    participant IAM as Rôle enervision-github-deploy

    JOB->>GH: demande un jeton, permission id-token write
    GH-->>JOB: jeton JWT signé, avec aud et sub
    JOB->>STS: AssumeRoleWithWebIdentity avec le jeton
    STS->>STS: vérifie la signature de GitHub
    STS->>IAM: lit la politique de confiance
    IAM-->>STS: aud = sts.amazonaws.com et sub = ce dépôt, branche main ou environment production
    STS-->>JOB: identifiants temporaires, valables 1 heure

    Le jeton contient notamment :

    Champ Valeur Vérifié par AWS
    aud sts.amazonaws.com le jeton est bien destiné à AWS
    sub repo:enervision-project@318340507/smart-energy-optimizer@1425361683:ref:refs/heads/main (jobs Changed services, Image …) ou …:environment:production (job Production) dépôt et branche, ou environment, autorisés

    Le rôle n'accepte que deux sub : la branche main de ce dépôt, et l'environment production, utilisé par le job Production. Un job lié à un environment reçoit un sub qui nomme l'environment et non la branche : c'est la règle Deployment branches de l'environment (main uniquement) qui garantit qu'on ne déploie que depuis main. Une PR, une autre branche, un fork ou un autre dépôt obtiennent un jeton avec un sub différent, refusé par AWS. C'est pour cela que, sur une PR, ci.yml construit les images sans pouvoir les publier.

    Format immuable du sub

    Le dépôt utilise le format immuable de GitHub : les noms de l'organisation et du dépôt sont suivis de leurs identifiants numériques (@318340507, @1425361683). Si le dépôt était supprimé puis recréé sous le même nom, il aurait un autre identifiant et ne pourrait pas déployer. Format à vérifier avec : gh api repos/enervision-project/smart-energy-optimizer/actions/oidc/customization/sub

    Le moindre privilège

    Même avec ce rôle, GitHub ne peut faire que le strict nécessaire :

    Action autorisée Ressource
    Pousser des images les dépôts ECR enervision/*
    Déposer des fichiers s3://enervision-deploy-<compte>/releases/*
    Lire les datasets DVC, publier une release de dataset ml/datasets/dvc/* (lecture) et ml/datasets/bootstrap/* (lecture, écriture) du datalake
    Envoyer une commande les instances enervision-app et enervision-monitoring, document AWS-RunShellScript
    Lire et écrire un paramètre /enervision/prod/deployed-sha et /enervision/prod/env/TRAINING_BOOTSTRAP_URI
    Écrire un paramètre /enervision/prod/env/ENERGY_API_USERNAME et ENERGY_API_PASSWORD

    GitHub ne peut pas lire les secrets de la base, créer ou supprimer des ressources, ni accéder au reste du compte. Les sauvegardes utilisent un rôle distinct (enervision-github-backup, voir Sauvegardes), et le plan Terraform des PR un rôle en lecture seule (enervision-github-plan).

classDef aws fill:#fff,stroke:#f08c00,stroke-width:2px
classDef plain fill:#fff,stroke:#333,stroke-width:1px
class GHA ci
class ROLE_GH,ROLE_EC2,PARAMS aws

style AWS fill:#d0d4da,stroke:#333
    • Deux rôles distincts : celui de GitHub (publier, déclencher) et celui de l'EC2 (lire les images, les fichiers de release et les secrets). Les secrets ne passent jamais par GitHub.
    • Secrets chiffrés dans SSM Parameter Store (SecureString), mot de passe de la base généré par Terraform : il n'est écrit nulle part dans le dépôt.
    • Réseau : seuls les ports 80 et 443 sont ouverts, vers Caddy. Pas de SSH : l'accès shell passe par aws ssm start-session, authentifié par le SSO.
    • IMDSv2 obligatoire et inaccessible depuis les conteneurs : un conteneur compromis ne peut pas récupérer les identifiants du rôle de l'instance.

    Dépannage

    Erreur Cause Solution
    Not authorized to perform sts:AssumeRoleWithWebIdentity le sub du jeton ne correspond pas à la politique de confiance (format, branche) vérifier github_oidc_sub_prefix dans variables.tf
    not authorized to perform: ssm:GetParametersByPath chemin lu différent de celui autorisé (/env et /env/ sont deux ressources IAM différentes) deploy.sh lit /enervision/prod/env, sans / final
    instance enervision-app introuvable instance arrêtée ou renommée aws ec2 describe-instances --filters Name=tag:Name,Values=enervision-app
    failed to register layer: … no space left on device /var/lib/docker plein (anciennes images) sur l'EC2 : df -h /var/lib/docker, sudo docker image prune -af, puis gh run rerun <id> --failed
    Échec : restauration de la configuration précédente des jobs ML le nouveau dataset ou la nouvelle image de prediction-service n'a pas pu être activé lire la sortie de la commande SSM dans le job Production ; l'ancienne version des jobs ML tourne toujours
    Le déploiement attend indéfiniment validation manuelle de l'environment production Review deployments → Approve and deploy dans le run du workflow Deploy

    Commandes utiles :

    gh run list --workflow services.yml          # derniers runs
gh run view <id> --log-failed                # logs du job en échec
aws ssm start-session --target <instance_id> # shell sur l'EC2
# puis, sur l'EC2 :
cd /opt/enervision
sudo docker compose -f compose.yaml -f compose.prod.yaml --env-file .env --env-file deploy.env ps
sudo docker compose -f compose.yaml -f compose.prod.yaml --env-file .env --env-file deploy.env logs -f web

    Revenir à une version précédente

    Faire un git revert du commit fautif sur main : la pipeline reconstruit et redéploie automatiquement le service concerné.
